# 0001 - 采用「环节 = 目录」的路线结构

- **状态**：已接受
- **日期**：2026-09-18
- **决策人**：作者本人

## 背景

仓库原有的 docs/ 是**按角色**组织的（02-product、03-ui、04-frontend……），适合当「知识库」查阅，但存在一个问题：**一个从零开始的人不知道先做什么后做什么**。角色是名词，行动是动词——独立开发者的真实工作是一条时间线：验证需求 → 定义产品 → 设计 → 搭架子 → 开发 → 上线 → 增长 → 迭代变现。缺这条线，知识库就是一堆散装零件。

## 决策

新增顶层目录 `phases/`，把独立开发全程拆成 **8 个环节**，**每个环节 = 一个目录 = 一份说明**，固定三件套：

```
phases/
├── README.md            # 环节地图 + 从零自检清单
├── 01-validate/         # 需求验证
├── 02-spec/             # 产品定义与任务拆解
├── 03-design/           # UI/UX 设计
├── 04-setup/            # 技术选型与脚手架
├── 05-build/            # 开发实现
├── 06-release/          # 部署与上线
├── 07-launch/           # 发布与增长
└── 08-iterate/          # 数据迭代与变现
    （每个环节目录内固定含三个文件）
    ├── README.md        # 做什么/产出/完成标准/陷阱
    ├── references.md    # 外部参考链接（开源/案例/官方文档）
    └── SKILL.md         # 给 AI 代理执行的标准技能
```

## 理由

- **两条主线互补**：`phases/` 管「什么时候做什么」（时间线），`docs/` 管「某件事怎么做深」（知识库）。环节文档用链接引用角色文档，**不复制内容**，避免两处维护。
- **三件套是固定模式**：说明（人读）、参考（外部链接）、技能（AI 执行）。模式固定后，新增环节有模板可抄，AI 代理也能按约定自动补全。
- **8 个环节**足够覆盖端到端，又不至于碎：每环节对应一次「可交付的产出物」，符合小步发布原则。

## 后果

**正面**：
- 从零开始的人有了明确路径：按 01→08 顺序走
- 每个环节天然沉淀出给 AI 的技能，形成「人做决策、AI 干活」的分工

**负面 / 代价**：
- `phases/` 与 `docs/` 存在主题重叠，必须靠「链接不复制」纪律避免内容漂移
- 多了一层需要维护的结构
