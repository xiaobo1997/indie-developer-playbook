# 原型优先：构思阶段就该看得见页面

> **解决什么问题**：想法还停在脑子里的时候，人最容易自欺欺人——「我觉得这样挺合理」。一旦把页面摆出来（哪怕只是灰盒子），逻辑漏洞、漏掉的页面、说不清的职责会立刻暴露。
>
> 本文是 [环节 03 UI/UX 设计](../../phases/03-design/README.md) 的方法论展开。核心主张一句话：**先想清楚做成什么样、有哪些核心功能，再谈好不好看；顺序反了，就会做出花里胡哨但没人用的东西。**

---

## 一、核心功能守门：砍到只剩一个动词

### 一句话测试

产品定义必须能写成这个句式，写不出来就是还没想清楚：

```
帮 [某类人] 用 [某个方式] 完成 [一件事]，比现在的办法更 [好在哪]。
```

关键约束：**「一件事」只能是一个动词**。如果你写的是「记录 + 分析 + 分享」，那是三个产品，不是 MVP。

- ❌ 「帮独立开发者管理项目、分析数据、协作沟通」——三个动词，做不完
- ✅ 「帮独立开发者把每天要做的事压缩成一页清单」——一个动词

### 判一个功能该不该进 MVP：三个问题

每个候选功能都问，三个都过关才留下：

1. **砍掉它，产品还成立吗？** 成立 → 砍掉。这条能砍掉一半功能。
2. **它是核心路径上的一步，还是核心路径旁边的装饰？** 用户第一次打开就会用到吗？不会 → 后置。
3. **它能不能用现成组件 / 现成服务顶上？** 能 → 不要自己做。

第 3 条最容易被忽略：登录、支付、推送、统计、客服——这些全都有现成方案，自己做的每一分钟都是从核心功能里偷的。

### 扩展性：什么该预留，什么不该

用户说的「未来怎么扩展」很容易滑向过度设计。判定标准是这句：

> **只有下个月就要做的东西，才值得现在留接口。**

| 该预留（改起来伤筋动骨） | 不该预留（改起来只是加代码） |
|---|---|
| 数据结构的字段设计（现在多留一个 `type` 字段，将来省一次迁移） | 抽象层、插件系统、配置化引擎 |
| 页面/路由结构（页面之间的关系改起来最贵） | 多主题、多语言、深色模式 |
| 核心实体的 ID 设计（用字符串还是自增整数） | 权限系统、角色体系 |
| 第三方服务的选型（换服务商的代价） | 「以后可能要做的」任何功能 |

右边那一列的共同点是：**它们听起来都很专业，但都是在为一个还不存在的未来付利息**。单人项目的正确做法是「先写死，等第二个同类需求出现时再抽象」——那时你才知道该抽象成什么样。

### 反花哨：一条硬标准

> **去掉它，用户还能完成任务吗？能，它就是装饰。**

装饰不是不能要，而是要放在功能确定之后，且成本可控。下面这些是最常见的「花里胡哨」，按危险程度排序：

| 装饰 | 真实成本 | 建议 |
|---|---|---|
| 自定义图标 | 每个 30 分钟，且和组件库风格打架 | 直接用现成图标库（heroicons / iconify） |
| 复杂动效 | 调试时间不可控，低端机掉帧 | 只在状态切换处加，其余用组件库默认 |
| 渐变 / 多层阴影 | 破坏设计系统的一致性 | 一个主色到底，阴影只用组件库的两档 |
| 插画 | 找不到合适的就变成丑 | 用 unDraw 现成的，或干脆不用 |
| 自创交互 | 用户不会用，等于没做 | 照抄成熟产品的交互，别发明 |

判断一个页面是不是「花里胡哨」，最有效的办法是**把它灰度化**：截图转成黑白，如果信息层级还清楚，说明结构是对的；如果转成黑白就分不清重点，说明你在靠颜色救结构——这时候该改结构，不是改颜色。

## 二、页面清单：每页只回答一个问题

接环节 02 的页面结构粗稿，每页一行。模板见 `pages.md` 产出物要求，核心是四列：

| 页面 | 用户进来干什么 | 离开时完成了什么 | 需要哪些组件 |
|---|---|---|---|
| 首页 | 看今天要做什么 | 知道下一步是什么 | 列表、空态提示 |
| 添加 | 记下一件事 | 事情已保存 | 输入框、按钮、Toast |

**硬性要求**：「用户进来干什么」只能写一件事。写不出一件事，说明这个页面职责不清，要么拆成两页，要么合并到别的页。

这一步最常漏的是三种状态，每一页都要有：

- **空态**：没有数据时显示什么（这是新用户看到的第一屏，也是最容易做好的一屏）
- **加载**：数据没到时显示什么（骨架屏 > 转圈 > 白屏）
- **错误**：失败时显示什么，能不能重试

只画「有数据」的样子就开工，上线后就是一片白屏。

## 三、可预览线框：让页面在写代码前就能看见

### 为什么草图不够

纸笔草图和 Excalidraw 解决了「结构」，但解决不了「感觉」。你需要能**在手机尺寸里、按真实比例**看到页面，才能回答这些问题：

- 一屏装得下吗？要不要滚动？
- 主操作的位置顺手吗？
- 信息密度会不会太挤 / 太空？
- 从上到下的阅读顺序，是不是就是任务顺序？

这些问题的答案，纸上看不出来。

### 三档保真度，按阶段选

| 保真度 | 工具 | 什么时候用 | 成本 |
|---|---|---|---|
| **线框**（灰盒子） | 本仓库的 [wireframe-preview.html](../../templates/wireframe-preview.html) | 刚有想法，验证结构和流程 | 几分钟 |
| **可交互原型** | Figma 原型模式 / 小程序开发者工具 | 验证流程走得通 | 半天 |
| **高保真** | v0.dev / bolt.new（Web）、直接写代码（小程序） | 准备开发了 | 1 天 |

**独立开发者的最优解通常是跳过第二档**：线框确认结构后，直接用真实组件（TDesign / Vant / shadcn）写代码，在真机上看。比在 Figma 里做高保真原型快，而且所见即所得——环节 03 已经写了「在 Figma 里精修一周是负资产」。

这里要划清一条线：**「视觉确认」值得做，「像素精修」才是负资产**。如果你看不出「好不好看」，把 AI 生成的方案摆进 Figma（或 [OpenDesign](https://github.com/nexu-io/open-design) 之类工具）看一眼方向是对的；但别在那里面调间距和对齐，细节交给组件库默认值。详见 [ai-as-designer.md](ai-as-designer.md#关于-figma视觉确认--像素精修)。

### 用 wireframe-preview.html

仓库自带一个单文件工具，打开即用、无需构建：

```bash
open templates/wireframe-preview.html
```

左侧用简单的标记语法写页面清单，右侧实时渲染成手机线框，**可以切换页面、切换空/载/错三种状态**。语法：

```
# 首页
[标题] 今天
[列表] 待办事项 x3
[按钮] 添加
[导航] 首页 / 统计 / 我的
```

打开时自带一个示例（待办类小程序），照着改即可。内容存在浏览器本地，刷新不丢。

**它的价值不是「画得好」，而是「够快」**——从想法到看见页面只需要几分钟，快到你愿意在动手写代码之前先试三个方案。

## 四、组件库认领：只做三个决定

选定组件库后，你不再是设计师，你是选择题考生。只做三个决定：

1. **主色**：一个。其余颜色用组件库默认的语义色（成功/警告/错误）
2. **圆角**：一个值，全局统一（8px 通常不会错）
3. **字号阶梯**：4-5 档，写进 `design-tokens.md`

其余全部用组件库默认值。**默认值的最大好处是一致性**——你随手调的每个值，都是一处潜在的「为什么这里和那里不一样」。

## 附：一个人怎么「找」 UI / UED / UX

单人项目没有设计师，这不是缺陷，是要绕过去的约束。五条现实路径，按性价比排序：

### 1. 抄成熟产品（成本 0，效果最好）

不是抄视觉，是抄**结构**：同类产品的列表页长什么样、表单页几步走完、空态写了什么话。

- [UI 参考项目库](ui-reference-projects.md) —— **本仓库自建，首选**。13 个经 GitHub API 逐个核实的开源项目（plausible / cal.diy / twenty / outline / TDesign 等），按页面骨架分类。**网站会打不开，仓库地址不会**——这是它比下面几个都可靠的原因
- [Mobbin](https://mobbin.com/) —— 真实移动端产品的完整流程截图，能按「列表页 / 引导流程 / 空态」筛，看的是上线产品在用什么。⚠️ **部分地区 / 网络下访问不稳定**，打不开时直接用上面的仓库
- 竞品直接截图 —— 你的同类产品就是最好的参考，装一遍、截全图
- Dribbble / Behance —— 只适合找视觉灵感，**不适合找功能参考**（上面的稿大多不考虑真实数据和边界情况）

### 2. 把设计决策外包给组件库

选一个组件库并严格只用它的组件，你就不再需要做「设计决策」——只剩「选哪个组件」。这是单例项目性价比最高的一步。

- 小程序：[TDesign](https://tdesign.tencent.com/)（腾讯，组件全）/ [Vant Weapp](https://github.com/youzan/vant-weapp)（有赞，社区大）/ [WeUI](https://github.com/Tencent/weui-wxss)（官方风格）
- Web：[shadcn/ui](https://ui.shadcn.com/)（复制粘贴，可定制）

### 3. 用 AI 生成（适合 Web，小程序慎用）

- [v0.dev](https://v0.dev/) —— 文字生成 shadcn UI 代码，Web 端效果很好
- bolt.new / Lovable —— 文字生成可运行应用

小程序侧的 AI 生成目前效果一般，生成的 WXML 常不符合小程序规范，建议直接手写 + 组件库。

### 4. 技能交换

用你的开发能力换设计师 1-2 小时。一个人做项目的优势是你可以提供对方需要的东西（做个小工具、搭个站）。1-2 小时足够让设计师指出你最致命的几个问题——比自己摸索一个月有效。

### 5. 用 5 人测试替代 UX 专家

可用性工程的经典结论：**5 个用户能发现约 85% 的可用性问题**（Nielsen）。你不需要 UX 专家，你需要 5 个真实用户对着原型走一遍核心路径，你在旁边闭嘴看着。

- 不要解释，不要提示，看他们在哪里卡住
- 卡住的地方就是问题，不用问他们「你觉得怎么样」
- 原型阶段做一次，上线后再做一次

### 该读的两本书

- 《Refactoring UI》—— 写给工程师的设计书，直接解决「我知道不好看但不知道怎么改」
- 《Don't Make Me Think》—— UX 入门，讲的是原则不是技巧

## 检查清单

进入环节 05 写代码之前，确认这几条：

- [ ] 产品定义能写成一句话，且只有一个动词
- [ ] 每个候选功能都过了三个问题，砍掉的写进了「以后再说」列表
- [ ] 只预留了下个月就要做的接口，没有为假想需求付利息
- [ ] 页面清单每页只回答一件事，且都映射到了组件库组件
- [ ] 每一页的空态、加载、错误三种状态都有定义
- [ ] 用线框工具看过至少三个关键页面，且是按手机真实比例看的
- [ ] 灰度化测试：转成黑白后信息层级还清楚
