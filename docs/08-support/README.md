# 08 · 客服角色目录

> 客服角色管"每个用户都被听见"。单人项目里客服是**洞察的入口**而不是成本：每条反馈都是产品方向的一手数据。原则：24 小时必回、道歉+解决优先于解释、反馈必归档。
> 对应环节：[环节 08](../../phases/08-iterate/README.md)（反馈是其复盘输入的一半）。

## 这个角色负责什么

| 负责 | 不负责 |
|---|---|
| 回复、安抚、给出临时方案 | 按用户要求改产品（排优先级归 PM） |
| 反馈分类归档、高频问题写 FAQ | 数据埋点与分析（看环节 08 度量） |
| 危机 first response（宕机/差评） | 根因修复（ DevOps/后端角色动手） |

**边界判定**：产出物是"已回应的用户 + 已归档的反馈"；产出物是"代码修改"就越界了。

## 独立跑完「客服工作」的流程

| 步 | 做什么 | 产出 | 耗时 |
|---|---|---|---|
| 1 | 开通道：产品内「反馈」入口 + 微信群 + 应用市场评论区 | 可触达的反馈入口 | 半天 |
| 2 | 回复：24h 内必回（复杂问题先回"处理中"） | 已回复工单 | 每日 15 分钟 |
| 3 | 归档：每条反馈记三件事（谁/场景/卡在哪） | 反馈汇总表 | 随回复 |
| 4 | 周清：聚类 + 挑高频写进 FAQ | FAQ 更新 | 每周 30 分钟 |
| 5 | 交复盘：把"卡在哪"清单交环节 08 周复盘 | 洞察清单 | 每周 10 分钟 |

**回复纪律**：道歉 + 解决 > 解释 > 争论（从不争论）。模板与危机处理（宕机/差评/数据泄露）见 [support.md](support.md)。

## 收什么 → 交什么

| 上游交给我 | 我交给下游 |
|---|---|
| 营销角色：新用户与其最初问题 | → PM 角色：反馈聚类清单（原话，不是转译） |
| DevOps 角色：事故通知（要不要给用户公告） | → 环节 08：每周"最痛的一件事"候选 |
| 用户：一切 | → FAQ/帮助文档（反馈固化成自助内容） |

## 真实参考（不用凭空想象）

- 小程序客服：MP 后台客服与客服消息能力（个人主体受限，以[官方](https://developers.weixin.qq.com/)为准）；轻量 Web 客服 [Crisp](https://crisp.chat/)（免费起步）、[GitHub Issues](https://github.com/)（开发者产品）
- 工具全景（Intercom/HelpScout/Tawk 对比）见 [support.md](support.md) 的客服工具节
- 本仓库技能：客服无独立 skill——回复模板直接用 [support.md](support.md) 的四段模板；反馈聚类与迭代决策走 [phases/08-iterate/SKILL.md](../../phases/08-iterate/SKILL.md)

## 新手最容易踩的坑

| 坑 | 为什么会踩 | 怎么避 |
|---|---|---|
| 和用户争论对错 | 被指责想自证 | 道歉+解决优先于解释；赢了争论输了用户 |
| 按声音大小排优先级 | 最吵的用户最显眼 | 反馈交 PM 对着北极星指标过滤，客服不拍板 |
| 反馈看过就丢 | 没有归档习惯 | 三件套归档（谁/场景/卡在哪），周清聚类 |
| 只救火不写 FAQ | 同一个问题答八遍 | 每周 ≥3 次同类问题 → 必须进 FAQ |
| 差评情绪化回击 | 公开场合的本能 | 差评处理模板见 [support.md](support.md) 危机管理节 |
