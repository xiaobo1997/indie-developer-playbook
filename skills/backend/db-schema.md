# 任务目标

把 PRD 的用户故事与功能范围转化为**可建库的数据模型**：实体、字段、关系、索引、访问权限，以及三条最容易踩的迁移坑。目标是照着建库不需要再做决定。

# 输入

1. PRD（用户故事、功能范围、非目标——非目标决定哪些表**现在不建**）
2. 数据库：PostgreSQL / MySQL / 云开发文档型 / SQLite（不确定时按"关系型优先"推荐）
3. 预估规模（个人项目默认 <1 万用户，按此给方案，不过度设计）

# 输出（严格按此结构交付）

```
## ER 概览
实体清单 + 关系一句话（User 1—N Project 等）

## Schema（完整可执行）
关系型：CREATE TABLE 语句（字段类型 / 非空 / 默认值 / 外键 / 唯一约束）
文档型：每个集合的文档结构示例 JSON + 字段说明

## 索引
只建"已知的查询会用到的"：每条索引注明服务哪个查询

## 访问权限
每张表/集合：谁能读、谁能写（对齐 docs/05 安全要求：默认拒绝、最小权限）

## 明确不建的
被"非目标"排除的实体 + 触发建表的条件（如"引入团队功能时再建 org 表"）

## 迁移与三个坑
1. 字段新增的默认值策略 2. 枚举用 text + 检查还是枚举类型 3. 时间统一存 UTC 的约定
```

# 执行步骤

1. 先读 [docs/05-backend/backend.md](../../docs/05-backend/backend.md) 的数据库选择与选型原则（关系型优先、不过早分库）
2. 从用户故事提名词找实体，从"以便…"找关系；每张表必须能指出它服务于哪条故事
3. 字段三问：非空吗？默认值？唯一吗？——一个都别含糊
4. 索引克制：只为已明确会做的查询建（列表页排序字段、外键、登录字段），不预防性堆索引
5. 权限按最小化写清；云开发集合逐个写权限模式
6. 写"明确不建的"清单——这是防过度设计的关键产出，不许省略

# 检查清单（输出前自检）

- [ ] 每张表/集合都对应至少一条用户故事，说不出就不该存在
- [ ] 主键、非空、默认值、唯一约束齐全，没有 `text` 一把梭
- [ ] 索引 ≤ 表数的 1.5 倍，每条有用途说明
- [ ] 权限默认最小化；管理接口没有混进业务权限
- [ ] "明确不建的"非空

# 边界（不要做什么）

- 不做分库分表、读写分离（<10 万用户不需要，见 docs/05 三阶段）
- 不引入 ORM 特有的魔法（schema 要在换 ORM 后依然成立）
- 不适用：需求没冻结（先走 `prd-template`，模型追着变的成本最高）；选 NoSQL 只是因为"听说快"（先给出关系型方案不行的事实依据再换）
