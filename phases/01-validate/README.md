# 环节 01 · 需求验证（Validate）

> **解决什么问题**：在写第一行代码之前，确认你要做的东西有人真的需要——避免花 3 个月做一个没人要的产品。独立开发最大的浪费不是做不出来，是做出来没人用。

## 你要做什么

1. **写下一句话假设**：`我相信【谁】在【什么场景】下需要【什么】来【解决什么痛点】`。写不出这句话，说明还没想清楚。
2. **竞品扫描（半天）**：找 3-5 个同类产品（小程序搜一搜、App Store、即刻、Product Hunt），各花 30 分钟回答：它解决什么？多少人用？怎么赚钱？差评在骂什么？——**差评就是你的机会清单**。
3. **找 3-5 个目标用户聊（3 天）**：不是问"你会用吗"（所有人都会客气地说会），而是问过去的行为："你现在怎么解决这个问题？上一次是什么时候？花了多久？最烦的是哪一步？"——这叫 [The Mom Test](https://www.momtestbook.com/) 方法。
4. **最小的行为验证（可选，1-2 天）**：做一个落地页/一段视频/一个群，看有没有人主动留下联系方式或提问。**行为 > 语言**。
5. **下决定**：做 / 不做 / 改了再做。写进验证报告，哪怕结论是"不做"——省下的几个月就是赚的。

## 产出物

`validation-report.md`（一页即可）：
- 一句话假设
- 竞品扫描表（产品 / 定位 / 收费 / 差评点）
- 3-5 段用户访谈摘要（原话！不要翻译成你的猜想）
- 结论：做 / 不做 / 调整后的方向
- 交给环节 02 的输入：目标用户 + 核心痛点

## 完成标准

- [ ] 能回答：谁、什么场景、什么痛点、现在怎么解决的
- [ ] 和 ≥3 个目标用户聊过，有访谈原话记录
- [ ] 能说出 3 个竞品和它们没满足的需求
- [ ] 写出了明确的做/不做结论

## 常见陷阱

- **为自己做却不承认**：想做的欲望会伪装成"用户需求"。对策：访谈里找和你不一样的用户。
- **问未来而不是问过去**："你会付费吗"得到客套话，"你上次为什么没续费"得到真相。
- **验证过度**：这是验证环节，不是调研报告比赛。3 天内出结论，超过一周说明在拖延。
- **跳过这个环节**：程序员最容易犯——"我先做出来再说"，然后做出第 N 个没人用的待办清单 App。

## 小程序主线注意点

- **验证渠道就在微信里**：搜一搜同类小程序看使用人数和评分；相关公众号评论区、豆瓣小组、即刻都是用户聚集地。
- **注意平台约束反推需求**：涉及支付、直播、社交的功能受主体和类目限制（见 [phases/README.md](../README.md) 硬知识 1、2），验证阶段就要把"平台做不了"的方向排除掉。
- **工具类需求验证成本低**：如果你自己就是目标用户（比如你每天要背单词），"自己先用起来"就是最诚实的验证。
