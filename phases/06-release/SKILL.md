# 任务目标

对准备上线的小程序（或 Web 服务）做一次**发布前审查**，输出明确结论：可提审 / 需整改（附整改清单）。这是环节 06 的质检关，宁可拦住，不可放行带硬伤的版本。

# 输入

1. 项目仓库访问权（代理读取代码与配置）
2. 目标平台与提审信息（服务类目、提审功能描述草稿，若有）
3. 本环节 README 的检查维度（合规三查、调试开关、监控、回滚）

# 输出（严格按此结构交付）

```
## 结论
可提审 / 需整改（二选一）

## 检查结果
### A. 代码与配置
| 检查项 | 结果 | 证据（文件:行） |
（调试开关、密钥硬编码、console.log 残留、.gitignore、版本号/环境配置）

### B. 小程序合规
| 检查项 | 结果 | 说明 |
（类目匹配/隐私指引/诱导分享文案/空占位页面/用户内容合规）

### C. 可观测与回滚
| 检查项 | 结果 | 说明 |
（错误上报就位/备份/回滚版本号记录）

## 整改清单（仅"需整改"时）
按 P0（不修不能提审）/ P1（提审后尽快）分级，每条：问题 → 怎么改 → 改完怎么验

## 提审建议
提审功能描述草稿（如实、具体）+ 建议提审时间（避开周五/节假日）
```

# 执行步骤

1. 逐项走 [skills/devops/deploy-checklist](../../skills/devops/deploy-checklist.md) 的通用项（读不到该文件则按本输出结构的 A/C 维度执行）
2. 合规三查：从代码中检索（诱导分享类文案、"敬请期待"空页面、采集了用户信息但未见隐私指引配置）；代码查不到的项标"需用户在 MP 后台确认"，不要臆断
3. 检查调试遗留：debug 开关、合法域名校验关闭、测试环境地址硬编码
4. 检查敏感信息：AppSecret、数据库密码、第三方 key 是否入库
5. 汇总结论；整改清单每条给具体做法与验证方式；引用官方规范处标注"以官方为准"

# 检查清单（输出前自检）

- [ ] 每个检查项都有证据（文件:行）或明确标注"需人工在后台确认"，没有臆断的 ✅
- [ ] 结论只有二选一，没有"基本可以"
- [ ] 整改清单按 P0/P1 分级且可执行（有问题、改法、验法）
- [ ] 没有把审核规则说成绝对（均以官方文档为准）

# 边界（不要做什么）

- 不代替用户做 MP 后台操作（类目修改、隐私指引填写——只能给步骤）
- 不借检查之名顺手重构代码（发现问题登记，不改）
- 不预测审核结果（只给"降低被拒风险"的依据，不打包票）
