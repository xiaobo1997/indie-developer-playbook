# 任务目标

以用户提供的**代码仓库 + 参数与权限清单**（ship-params.yaml）为唯一输入，把产品发布到清单里列出的每个平台，**最低交付到"提交审核完成"**（Web 路线交付到"线上可访问"），并以端到端验证作为收尾。铁律：**先预检后动手**——预检不过的平台不动工，绝不做到一半才发现做不了。

# 输入

1. `ship-params.yaml`（产品信息、目标平台列表、各平台参数）
2. 代码仓库访问权（AI 自行 clone/读取）
3. 各平台权限（yaml 里标注 🔒 的由用户按指引提供或现场处理）

# 输出（严格按此结构交付）

```
## 总报告
- 预检结论：每平台 pass / blocked（blocked 的写明缺什么、补办要多久多少钱）
- 本次完成：平台 → 交付程度（提审完成 ✅ / 上线 ✅ / 卡在 X）
- 你需要做的下一步：逐条列出（人工停机点 + 补办材料）

## 各平台明细（每平台一节）
- 执行了哪些步骤（对照 platforms/*.md 的流水线编号）
- 证据：命令输出摘要 / 返回 JSON 关键字段 / 截图描述 / 版本号与提审单号
- 端到端验证结果：核心链路在真实环境调通的证据
- 遗留与风险

## 时间线
做了什么（时间序），方便你复核
```

# 执行步骤

1. **读参数与代码**：解析 yaml；clone 仓库；确认目标平台列表与 `platforms` 字段一致，有出入先问
2. **可行性预检（强制第一关）**：逐平台跑 [feasibility-check.md](feasibility-check.md)，产出 go/no-go；**任何 blocked 平台不进入后续步骤**，把补办路径写进总报告
3. **构建验证**：对 pass 平台先在本地/CI 完成"能构建出产物"的验证（小程序 npm 构建、iOS archive、Android bundle、Steam 可执行包、Web build）——构建失败即停，报告原因
4. **逐平台执行管线**：按 `platforms/<平台>.md` 的流水线执行；每完成一步打勾并记录证据；**人工停机点（👤）停下来给指引**，等确认再继续
5. **端到端验证（收尾硬标准）**：
   - Web：外部 `curl https://域名` 200 + 核心链路（注册→核心功能→持久化）走通
   - 小程序/小游戏：体验版真机打开 + 核心接口调用 200
   - iOS：TestFlight 构建真机安装并打开
   - Android：内测轨道真机安装并打开
   - Steam：depot 上传成功 + 商店页可访问（提审中）
6. **提交审核**：能 API 提审的（小程序/iOS/Android-GP）用 API 提审并记录审核单号；console 提审的（Steam、国内商店）准备好全部素材与表单值，给用户"逐字段填写指引"
7. **输出总报告**；有 blocked 项时同时输出"补办清单"（材料、渠道、预计周期）

# 检查清单（输出前自检）

- [ ] 没有任何平台跳过预检直接动工
- [ ] 每个宣称"完成"的步骤都有证据（输出/单号/版本号），无一处"应该成功了"
- [ ] 端到端验证是真实环境（真机/外部网络），不是本机 localhost 自嗨
- [ ] 用户垫付金额为零；所有付费动作都发生在 👤 停机点
- [ ] 没有伪造素材（截图/评价/数据）；提审信息与实际功能一致
- [ ] blocked 平台给了可执行的补办路径（缺什么/去哪办/多久/多少钱）

# 边界（不要做什么）

- **不垫付、不代持账号、不绕过任何平台审核机制**（买量、换审、马甲包一律拒绝）
- 不开发业务代码本身——用户给的是"可发布的代码"；构建失败属于预检/报告范畴，不属于本技能的修复范畴（可给修复建议）
- 不预测审核结果，只保证"提交合规、信息真实"
- 不在报告中输出任何 🔒 明文（密码/私钥/secret）
- 反向触发：平台列表为空或代码无法构建 → 先解决输入，不进入管线；用户只想要某一个平台 → 跳过其余平台，不扩大范围
