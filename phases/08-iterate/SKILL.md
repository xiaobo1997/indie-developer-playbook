# 任务目标

接环节 07（已有真实用户），作为每周例行的复盘引擎：把本周数据 + 用户反馈转化为**下周一到两个明确的迭代决策**，并沉淀成规范的记录。核心纪律：只定 1-2 个改动，宁可少而透。

# 输入

1. 本周数据（从 MP 后台/Web 分析读出：北极星指标、活跃、留存、流失最重的页面；读不到精确数就给大概值）
2. 本周用户反馈原始记录（群聊/私信/评论，原话最好）
3. 上一轮复盘定下的改动及其结果（第一周没有就跳过）
4. 当前卡住的变现门槛（可选）

# 输出（严格按此结构交付）

```
## 本周一页
- 北极星指标：本周值 vs 上周值（趋势 ↑↓→）
- 最刺眼的一件事（数据或反馈，一句话）
- 用户反馈聚类：3 类以内（每类：原话摘录 1-2 条 + 出现次数）

## 诊断
最痛的问题是什么？它属于：获客/激活/留存/变现 哪一环？
（引用反馈原话与数据作为证据，不靠感觉）

## 下版决策（1-2 个，不许更多）
| 改动 | 对应证据 | 完成标准（可验收） | 预估 |
每个改动已通过砍功能四问：30 天内能做完？有人要？自己会用？能带来用户？

## CHANGELOG 草稿
按 templates/changelog-template.md 格式，写好本周版本条目（用户视角语言）

## ADR 判断
是否需要写决策记录：是（给出 ADR 标题与背景要点）/ 否（说明为何只是常规迭代）

## 变现进度
当前门槛是什么，本周动作是否让门槛更近（没有变现计划则写"未启动"）
```

# 执行步骤

1. 先复核数据输入：缺哪项就标注"缺"，不要编数；趋势判断保守
2. 反馈聚类：按场景而非字面功能聚类；区分"用户说要什么"（方案）与"用户卡在哪"（问题），诊断只基于后者
3. 用砍功能四问过滤候选改动，硬性输出 1-2 个；被砍掉的候选记入"备选池"留档
4. 为每个改动写可验收的完成标准（对齐环节 02 任务卡粒度，可直接进 tasks.md）
5. 按 Keep a Changelog 风格起草条目：写给用户看（"新增手动加词"），不写实现细节（"重构了词库模块"）
6. ADR 判断标准：方向变化/结构决定/影响多环节 → 写；纯 bug 修与常规功能 → 不写

# 检查清单（输出前自检）

- [ ] 没有编造任何数据；缺失项明确标注
- [ ] 诊断引用了至少一条反馈原话或一个数据点作为证据
- [ ] 下版决策 ≤2 个，每个都有可验收标准与预估
- [ ] CHANGELOG 是用户视角语言，没有实现术语
- [ ] 备选池留了档（被砍的候选没有丢）

# 边界（不要做什么）

- 不推翻产品定位（要转向时输出"建议进入 ADR 讨论并回到环节 01 复核"，不直接宣布转向）
- 不替用户做变现动作（如开通流量主、申请商户号——只给步骤与门槛）
- 不建议污染数据的增长手段
- 本技能输出的是决策建议，最终取舍由用户拍板——在结尾明确提示"请确认后再排入下周任务"
