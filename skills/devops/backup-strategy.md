# 任务目标

为用户的数据库与关键资产生成**最小可执行的备份方案**，核心产出不是"备份了"，而是"验证过能恢复"。一个从未做过恢复演练的备份等于没有备份。

# 输入

1. 数据资产清单：数据库（类型/托管方）、文件存储、代码仓库、配置与密钥（密钥不备份内容，只备份"去哪找回"）
2. 托管形态：云开发 / Supabase / 自建服务器
3. 数据重要度：可容忍丢失多久的数据（个人项目默认 ≤24h）

# 输出（严格按此结构交付）

```
## 备份矩阵
| 资产 | 备什么 | 频率 | 存到哪 | 保留多久 | 自动化方式 |
（遵循 3-2-1：≥3 份副本、≥2 种介质、≥1 份异地；托管平台自带备份要写明它在哪、够不够）

## 自动化配置
每条资产的定时任务 / 平台功能的开启步骤（可复制的命令或后台路径）

## 恢复演练清单（每季度一次，30 分钟）
1-2-3 步：在隔离环境拉起 → 用最近备份恢复 → 校验关键数据条数与抽样内容
每步写"看到什么算成功"

## 已知缺口
当前方案做不到的（如：文件存储没异地、密钥无托管），按风险排序，各给一条补齐建议
```

# 执行步骤

1. 先读 [docs/06-devops/devops.md](../../docs/06-devops/devops.md) 的备份策略小节（3-2-1 法则与 pg_dump 示例）
2. 盘点资产时不漏"最容易被忘的三样"：数据库、用户上传文件、环境变量/密钥清单（密钥本体不进备份，记录找回路径）
3. 托管平台自带备份（Supabase/云开发快照）先确认覆盖与保留期，不够再补自动化
4. 自建部分给 cron + 压缩 + 异地上传的完整可复制脚本（参考 docs/06 的 pg_dump 模式）
5. 恢复演练清单是本技能的灵魂——没有"验证恢复"环节的方案打回重做

# 检查清单（输出前自检）

- [ ] 3-2-1 逐项核对过，不满足处如实写进"已知缺口"而不是假装满足
- [ ] 每条备份都有自动化方式（手动备份活不过第三周）
- [ ] 恢复演练有明确的成功判据
- [ ] 密钥没有出现在任何备份内容里

# 边界（不要做什么）

- 不做容灾架构（多区域/双活是 10 万用户后的事）
- 不备份用户数据到开发者个人设备（合规风险，见 docs/09 法务基础）
- 不适用：数据全在代码仓库里的纯静态项目（版本控制已是备份）；还没上线的项目（先上线，上线当天必备份）
