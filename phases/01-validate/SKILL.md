# 任务目标

对用户提出的产品想法，产出一份**一页需求验证报告**，明确结论：做 / 不做 / 调整后再验证。禁止在没有证据的情况下鼓励用户"值得做"。

# 输入

用户提供（有多少给多少，缺失的向用户追问一次）：
1. 产品想法的描述（一两句话即可）
2. 目标用户是谁（如果用户自己就是目标用户，说明这一点）
3. 计划平台（微信小程序 / Web / App 等）

# 输出（严格按此结构交付）

```
## 一句话假设
我相信【谁】在【什么场景】下需要【什么】来【解决什么】。

## 竞品扫描
| 产品 | 一句话定位 | 收费方式 | 已知弱点/差评点 | 对我的启示 |
（至少 3 行；信息不足时列出可去哪里查，不要编造数据）

## 访谈提纲
5-7 个问题，全部问过去行为而非未来意愿；附"为什么这样问"的一句话说明。

## 风险与平台约束
列出该想法在目标平台上的硬约束（主体资质/支付/类目/审核），标注"以官方文档为准"。

## 结论
- 判定：做 / 不做 / 调整后再验证（三选一，不许含糊）
- 依据：用已有事实说明
- 下一步：交给环节 02 的输入（目标用户 + 核心痛点 + 平台）
```

# 执行步骤

1. 复述用户的想法，检查是否有歧义，先追问补齐输入
2. 竞品扫描：基于你掌握的知识列出同类产品；对不确定的信息明确标注"待验证"并给出验证渠道
3. 写访谈提纲：每个问题对照 The Mom Test 原则自检（是否在诱导？是否问的是过去？）
4. 平台约束检查：对照仓库 `phases/README.md` 的「小程序 8 件硬知识」（若平台是小程序）
5. 给出结论，宁可保守：证据不足时判定为"调整后再验证"，并写清缺什么证据

# 检查清单（输出前自检）

- [ ] 没有编造竞品数据（用户量、收入），不确定的地方都标了"待验证"
- [ ] 访谈问题没有一个能被"会的/好的"这种客套话打发
- [ ] 结论是明确三选一，不是"可以考虑一下"
- [ ] 平台约束部分链接了官方文档或标注了以官方为准

# 边界（不要做什么）

- 不做产品功能设计（那是环节 02 的事）
- 不写代码、不做落地页
- 不因为用户兴奋就顺着说"好想法"——你的价值是泼冷水和找漏洞
