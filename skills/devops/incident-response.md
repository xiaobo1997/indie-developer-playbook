# 任务目标

为用户的线上产品生成一份**一页事故响应 runbook**（平时写好，出事照做）；若正在发生事故，则按 runbook 结构直接输出当前处置步骤。

# 输入

1. 产品形态：小程序（云开发/自建后端）/ Web SaaS（托管平台 + 数据库）
2. 技术组件清单（托管在哪、数据库是什么、有无监控）
3. 当前状态：平时预防 / 事故进行中（后者需附现象描述）

# 输出（严格按此结构交付）

```
## 事故分级
| 级别 | 定义 | 响应时限 | 典型例子 |
（P0 全挂/数据丢失；P1 核心功能不可用；P2 非核心受损；P3 观感问题）

## 分级处置卡
每级三段：先做什么（≤3 个动作）/ 通知谁（用户公告？先不发？）/ 什么信号算恢复

## 通知模板
P0/P1 的用户公告草稿（发生了什么 / 影响 / 临时方案 / 下次更新时间），不写技术细节堆砌

## 复盘模板（事后 48 小时内填）
时间线 / 根因 / 为什么监控没提前叫 / 一条防复发动作（只留一条，写进任务卡）

## 单人项目的三条铁律
先止血再查因（回滚优先于 debug）/ 不在事故中重构 / 全程记录时间线
```

# 执行步骤

1. 先读 [docs/06-devops/devops.md](../../docs/06-devops/devops.md) 的监控与安全清单，runbook 与已有监控对齐
2. 按组件清单写"典型故障 → 判定 → 动作"：托管平台故障 / 数据库打满 / 密钥泄露 / 依赖服务挂 / 被刷
3. 每个动作必须是单人可执行的（"回滚到上一版本号"而不是"排查问题"）
4. P0 数据丢失场景必须含：停写入、用最近备份恢复的命令级步骤（备份策略见 `backup-strategy`）
5. 事故进行中模式：先按现象定级 → 只输出该级处置卡 → 恢复后再补复盘

# 检查清单（输出前自检）

- [ ] 动作全部具体可执行（有命令/有按钮位置），没有"尽快修复"
- [ ] 分级时限符合单人现实（不是 7×24 SLA）
- [ ] 有数据丢失路径的恢复步骤，且引用了真实存在的备份
- [ ] 复盘模板只要求一条防复发动作（贪多就不会做）

# 边界（不要做什么）

- 不替用户决定"要不要公告"以外的商业决策（公告内容给草稿，发不发用户定）
- 不在事故进行中做根因分析长文（先恢复，复盘事后做）
- 不适用：还没有线上产品（先走环节 06 上线）；想要复杂 on-call 体系（单人项目用不上，别过度建设）
