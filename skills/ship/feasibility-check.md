# 任务目标

在**任何**发布动作开始前，对 ship-params.yaml 列出的每个平台做硬门槛核查，输出**逐平台 go/no-go 报告**。目的：把"做到一半发现做不了"变成"开工前十分钟就知道"。宁可拦住，不放行带硬伤的开工。

# 输入

1. ship-params.yaml（目标平台 + 已有参数）
2. 代码仓库（只读，验证可构建性）
3. 用户对追问的回答（缺失项一次性问齐）

# 输出（严格按此结构交付）

```
## 预检总表
| 平台 | 判定 | 硬伤（如有） | 补办路径 | 补办周期 | 补办费用 |
判定：go / blocked（有不可绕过的门槛未满足）

## 逐平台核查明细
每平台一张表：| 检查项 | 要求 | 现状 | 证据/依据 |
（每张表的最后一行固定是"代码可构建性"的实测结果）

## 你现在要做的（如果全部 go）
按顺序列出开工前的授权动作（AK/私钥/API Key 的提供方式）

## 补办清单（如有 blocked）
材料清单 → 提交渠道 → 预计周期 → 费用；能并行的标出来
```

# 执行步骤

1. 读 [README.md](README.md) 的平台矩阵，按 [platforms/](platforms/) 各文件的「硬门槛」表逐项核查
2. **代码可构建性是每平台的必测项**：小程序（依赖安装 + npm 构建）、iOS（pod/Xcode archive 或至少 pod install 可解析）、Android（gradle bundle task 可运行）、Steam（可执行文件存在/打包脚本可跑）、Web（build 成功）。构建失败 = blocked，报错误原文
3. 资质类核查（主体/软著/类目/测试员要求）以 platforms/*.md 引用的官方文档为准，标注"以官方为准"
4. 费用与周期写区间不给精确承诺；所有需要用户花钱的项都单独汇总
5. blocked 项必须给补办路径——预检的价值不是否决，是给出"多久能变成 go"

# 检查清单（输出前自检）

- [ ] 每个目标平台都有判定，没有"待定"混入 go
- [ ] 代码可构建性是实测（跑了构建命令），不是推断
- [ ] 全部需要花钱/等周期的项已汇总成补办清单
- [ ] 没有输出任何 🔒 明文

# 边界（不要做什么）

- 不做任何发布动作（预检是只读关：不改云端状态、不注册账号、不付费）
- 不因"用户着急"放行 blocked 项；可以说明风险，判定不变
- 不适用：只发布 Web 且已有部署清单的场景（直接走 checklist-zero-to-prod，本技能仍建议跑"代码可构建"一项）
