# 任务目标

把一段功能描述（或一份 PRD 的功能清单）改写成**一组用户故事**，每条附可勾选的验收标准，供排期、拆任务卡和验收使用。

# 输入

1. 功能描述（一段话或功能清单）
2. 目标用户画像（有几种用户就要分几种角色写）

# 输出（严格按此结构交付）

```
## 用户故事
### US-N: [故事名]
> 作为【具体角色】，我想【做什么】，以便【得到什么价值】。

**验收标准**：
- [ ] （可勾选、可观察的行为，不写"正常工作"）
- [ ] 异常路径至少一条（空数据 / 失败 / 权限不足）

## INVEST 自查
| 故事 | 独立 | 可协商 | 有价值 | 可估算 | 足够小 | 可测试 | 问题 |
（不合格的给出拆分建议）

## 超出故事范围的（明确不做）
```

# 执行步骤

1. 先读 [docs/02-product/product-management.md](../../docs/02-product/product-management.md) 的用户故事与优先级小节
2. 识别故事里所有的角色（游客 / 注册用户 / 管理员…），一个故事只写一个角色
3. 改写格式：价值部分必须回答"不做这件事用户损失什么"，答不出就删
4. 每条故事写验收标准：正常路径 + 至少一条异常路径，全部可勾选
5. INVEST 六项自查，过大的故事给出拆分建议（拆成 2-3 条）
6. 列出"改写过程中发现但明确不做"的需求，防止范围蔓延

# 检查清单（输出前自检）

- [ ] 没有一个故事里塞了两个角色或两个动词
- [ ] 验收标准没有"尽快""友好地"这类不可验收词
- [ ] 每条故事的价值都成立（砍掉测试通过）
- [ ] INVEST 表没有空列，不合格项都有拆分建议

# 边界（不要做什么）

- 不决定优先级顺序（那是 P0-P2 排序问题，用 RICE/MoSCoW，见 docs/02）
- 不写实现方案（故事描述"什么与为什么"，不描述"怎么做"）
- 不适用：需求还没验证（先走环节 01）；要的是完整 PRD（用 `prd-template`）
