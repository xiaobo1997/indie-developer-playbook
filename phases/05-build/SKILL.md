# 任务目标

领取**一张任务卡**（环节 02 产出的 tasks.md 中的一条），交付通过其「完成标准」的可运行实现。核心原则：最小改动、可验收、不越界。

# 输入

1. 任务卡（编号/做什么/完成标准/依赖）
2. 项目仓库的 AGENTS.md（技术栈与代码约定）
3. 相关的现状代码（代理自行读取；找不到就问用户，不要凭空假设文件结构）

# 输出（严格按此结构交付）

```
## 实现说明
做了什么（3-5 句）、关键取舍（如有分叉点，说明选了哪条路、为什么）

## 改动清单
文件 → 改动摘要（新增/修改/删除，一行一个）

## 自测结果
对照任务卡完成标准逐条：✅/❌ + 怎么验证的
无法自测的项（如真机表现）明确标注"需要用户真机验证"

## 验收步骤（给用户）
1-2-3 步骤：在哪个页面、做什么操作、应看到什么

## 遗留与建议
发现但未处理的问题（如顺手看到的 bug、值得开新任务卡的优化）——只登记不动手
```

# 执行步骤

1. 读 AGENTS.md 与相关代码，确认目录、命名、样式约定；找不到约定时遵循代码现状（一致性 > 个人偏好）
2. 只实现任务卡描述的功能；完成标准里没提的不做（哪怕"顺手就能加"）
3. 写代码：优先复用组件库现成组件与项目内已有工具函数；新依赖默认不加，确需添加时在实现说明里给理由
4. 自测：能跑测试的跑测试；小程序项目给出"在开发者工具中如何验证"的具体操作
5. 检查越界：git diff 确认没有任务卡之外的改动；有必要的连带改动（如改公共组件）在实现说明中单独说明
6. 检查硬伤：无残留调试代码、无硬编码密钥/URL、无未处理的空值崩溃路径

# 检查清单（输出前自检）

- [ ] 完成标准逐条核过，没有一条被悄悄降级
- [ ] 改动范围 = 任务卡范围，越界改动为零或已显式声明
- [ ] 空数据、异常输入、加载失败三条路径有着落
- [ ] 新增依赖为零，或附有充分理由
- [ ] 没有把"需要用户真机验证"说成"已验证"

# 边界（不要做什么）

- 不重构任务卡外的代码，不"顺便优化"
- 不修改数据库结构/接口契约（发现必须改时，停下来向用户说明，等确认）
- 不一次领多张卡：一张卡一次交付，验收通过再领下一张
- 遇到阻塞（缺上下文/技术不可行）超过两次尝试仍无解：停下来，输出"阻塞报告"（卡在哪、试过什么、需要用户补什么信息），不要硬编一个看起来能用的版本
